Case study · coding-agent memory

Does memory stop coding agents from repeating mistakes?

Six experiments, from an offline retrieval benchmark to a controlled 125-run replay with a real agent. Memory measurably improved which file an offline ranking put first. No clear effect on what a real agent did was detected.

6 experiments442 held-out retries576 agent runs in v5125 in the final replay

The question

Teams that run coding agents build up history: past sessions, failed attempts, review comments, decisions. A shared memory layer promises to hand the right piece of that history to the next agent, so it does not repeat old mistakes. This project asked a narrow, testable version of that promise: when a coding agent is given the relevant lesson from earlier work, does it avoid the mistake, and does memory beat simply reading the repository?

The starting hypothesis had two steps. A good retriever would find past work that points to the right code, and an agent given that pointer or lesson would work faster and avoid known mistakes. The plan was to measure step one cheaply and offline, then test step two with a real agent.

The answer, in three numbers

These results hold for the settings tested: one agent, one model family, public Python data for the retrieval work and five TypeScript tasks for the replay. They are not a verdict on agent memory in general.

The journey

v1 was built first and then reviewed. From v2 on, each step was pre-registered and frozen with a git tag before its held-out data was scored, and every step was checked by an independent reviewer that could read the code and data but not change them. Each result decided the next step.

The promising finding: memory of a failed attempt

An unsolved issue has no merged fix, so fix history cannot help with it. But a failed attempt has already explored the code. The handoff ranks the files that attempt edited and opened, with a fix-history fallback, and hands them to the next attempt.

The pre-registered comparison is +9.0 points. An independent reviewer found a fairer baseline: give the real retry the same fallback. Against it the lead is +5.7 [+1.4, +10.6], and that comparison was made after the fact. Most of the gain comes from retries that stall before opening anything. A failed attempt holds about what the next attempt would find by itself, so its value is a head start and a fallback.

This measures file identification, not task completion. That is what v5 tested next.

Why better retrieval was not enough

The handoff went in front of a real agent (mini-swe-agent with DeepSeek Flash): 144 tasks, two arms, two repeats, 576 runs. Mean steps went from 19.73 to 19.19, a 2.7% drop whose interval includes zero. Cost rose 4.4%. The agent solved 86.1% without the hint and 87.5% with it. The median step at which it first opened a needed file went from 2 without the hint to 1 with it.

The pilot for that run caught a leak worth knowing about. The public evaluation images still held the future fix in their git history, and the agent found it: 25 of 30 runs printed the real fix (per the run notes). That run was thrown away, and every image is now cleaned and checked before use.

So if memory matters, it has to carry knowledge the agent cannot rediscover by reading the repository: a decision a reviewer made, or a mistake that only shows up later. That is what the final experiment tested.

The controlled 125-run experiment

Five tasks built around mistakes a reviewer had flagged earlier, taken from the author's own agent-built TypeScript projects. For three of them the agent's real earlier attempt that made the mistake is kept as a control. Five memory conditions, five seeds each, the analysis frozen before the first paid request. A run passes if the task and regression tests pass, and avoids the mistake if, in addition, withheld memory tests for that exact earlier mistake pass.

  • none, and instructions (one general build brief shared across projects)
  • retrieved: BM25 over the earlier review records, cut to 18,000 characters
  • oracle: the two hand-picked lessons, padded with random records to the same size
  • random: same size, no hand-picked record

What failed, and why

  • Ceiling. On lock, verifier and simlink the agent avoided the mistake without memory. The repository already showed the right pattern, or the task asked for it. Memory had nothing left to add.
  • Floor. On fczero every run passed the task, but none fixed the earlier mistake, not even with the hand-picked lesson in context. The lesson was one line inside long review records about another project, and the agent gave priority to the explicit request in the task.
  • Retrieval. Keyword search over raw review records put the useful lesson into the memory text for one task of five.
  • The one interesting cell. On onnx, retrieved memory avoided the mistake 5 of 5 times and every other condition 1 or 2. It is one task with 5 seeds, and the lesson was already in the repository, so it is a hint for a follow-up, not evidence.

The engineering that made the result trustworthy

  • Evaluation integrity. Fourteen freezes before the paid grid, each with a written reason and all before any counted run. None changed the tasks, memory texts, conditions, seeds, tests or comparisons. Some refined how crashed or cut-off runs are handled. The analysis refuses to run if any frozen input, image or installed package changed.
  • Isolation. Redacted single-commit snapshots, containers with no network, a host sandbox that denies writes to the source repositories, and a before/after snapshot of every file there, caches included.
  • Privacy. The first full paid run was stopped by its own audit: an internal branch name had reached the model through git log output. The fix was a fail-closed scan of every outgoing request, conversation history and tool output included. Later, when the disk filled, that boundary refused a request carrying an error message with a local path, and the run stopped itself.
  • Budget control. A hash-chained, append-only ledger reserves each request's worst case under a lock before it is sent, and settles it after. Ten review rounds before the grid found ways money could leak (a crash before logging, two processes spending at once, a reachable total of $10.02) and each was closed.
  • Independent verification. A read-only reviewer (an independent second model) recomputed the replay's per-task rates, comparisons and intervals from the raw rows. They matched. It found no gaming of the grading, and two small reporting gaps that are disclosed below.

Lessons for practical agent-memory systems

Drawn from these results at this scale. They are working conclusions, not general proofs.

  1. Measure behaviour, not retrieval. A clear offline retrieval gain (v4) showed no clear effect on a real agent (v5).
  2. Memory competes with the repository. When the lesson is visible in the code, a strong agent finds it, and memory added tokens with no clear effect detected.
  3. Raw history is a poor memory format. A one-line lesson inside long records showed no clear effect on behaviour, even when it was hand-picked.
  4. Keyword retrieval over review prose misses. The useful lesson reached the memory text for one task of five.
  5. Leaks are everywhere. Git history in evaluation images, caches in node_modules and branch names in tool output all leaked or nearly leaked here. Check the whole request, not only the prompt.
  6. Design the money path like a database. Reserve before sending, settle after, latch every failure, never reset.

What we would test next

None of this was built or run.

  • 6 to 8 tasks where the lesson is absent from the repository, so memory has room to help.
  • A distilled-lesson condition, a short specific rule, next to raw records.
  • Retrieval that indexes individual lessons rather than whole review documents.
  • The two reporting gaps fixed before a new freeze.

Conclusion and limits

The evidence moved the question from "can memory find the right file?" (yes, measurably) to "does it change what the agent does?" (no clear effect detected in these settings). The results did not clearly support the starting hypothesis, and each step of that, including the negative ones, is on the record.

Limits: one agent and one model family for the agent experiments. Four primary replay tasks, two of them at the ceiling. Memory as raw records, not distilled lessons. File overlap as a proxy in v1 to v4. Two known reporting gaps in the frozen replay analysis: the secondary comparisons have no bootstrap intervals, and token counts leave out 32 paid responses that followed format errors (costs are complete). None of this shows that agent memory does not work in general.

v4: the retry handoff

All 80,036 pinned attempts, split by a hash of the task id (60/20/20, with the earlier benchmark's repositories always in train). Attempts are independent samples, so "retry" follows dataset row order, not real time. The unit is the first retry after a failed first attempt. Two other ideas were checked on train first and dropped: a known-failure warning (retries succeed 1% of the time) and a recurring-error warning (76% against 71% precision, no clean label). Reviews and what they changed

Before results: 14 freezes

Freezes 1 to 3 came from pre-registration reviews (crashes counted as missing, a minimum of 3 complete seeds, a written rule for "lesson in repo"). Freeze 4 was the privacy repair. Freezes 5 to 13 followed nine NO-GO rounds from a read-only second-model review, almost all about money and failure handling. Freeze 14 only changed how the base image is looked up. All of this happened before any counted run, and no freeze changed the tasks, memory texts, conditions, seeds, tests or the three comparisons.

One finding mattered for the result itself: runs that hit the model's context limit were being scored as unchanged code, which would have penalized the long-memory conditions. It was fixed before any grid run.

After results: independent recomputation

The reviewer recomputed the per-task rates, the three comparisons and the Wilson intervals from the raw rows and they matched. It read diffs and transcripts for the surprising cells, found no gaming of the grading, and verified the ledger's hash chain and the cost reconciliation. Two reporting gaps were found and are disclosed: the secondary comparisons have no bootstrap intervals, and token counts miss 32 format-error responses.

Inconsistencies found in the records
  • The discarded v5 pilot run is described both as "29 of 30 runs searched git history" and "25 of 30 printed the real fix". Different measures, both true.
  • The replay cost estimate cites 603 earlier runs, while the counted v5 runs add up to 606.
  • The grid first ran with a $10 cap and the resume with $9.99. Both sit inside the approved $10, and the ledger counted everything cumulatively.
  • onnx and verifier were first judged "lesson not in the repo" in the pilot, then classified "in repo" by the rule frozen into the analysis. The frozen rule is used.

Reproduce

v1 to v4 run offline from public data: make test, make data-check, make experiment, then tools/unseen.py and tools/handoff.py on the pinned files. v5 and the replay need paid model calls and Docker images. The replay also needs task repositories, memory texts and per-run rows that are not public, so the replay and its frozen analysis cannot be rerun from this repository.
